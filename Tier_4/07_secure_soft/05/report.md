#### Table 1: Configuration errors

| File                    | Error                           | Why it is an error                                                         | How to fix                                                 |
| ----------------------- | ------------------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `crypto_config_le.yaml` | Risky JWT algorithm             | HS256 is symmetric, each service must know the secret -> wide blast radius | Use asymetric signing algoritm RS256 from jwt library      |
|                         | Hardcoded secret                | Difficult to rotate, can end up in logs, CI artifacts or public repo       | Load the secret from a secret manager and rotate regularly |
|                         | Fixed salt                      | Predictable, easy to break                                                 | Random salt per password generated by the hashing library  |
|                         | Unsafe encryption algorithm     | DES is obsolete, small key size, brute-force feasible                      | Use a modern algorithm such as AES-256-GCM                 |
|                         | Hardcoded key storage           | Difficult to rotate the key, can end up in logs, CI artifacts, public repo | Use a secret manager such as KMS                           |
| `crypto_config_mi.yaml` | Small key size                  | 2048-bit key is quite small for the modern applications                    | Use 3072+ keys                                             |
|                         | Week parameters for Argon2      | Too cheap params for Argon2, it allows high-speed offline cracking         | More memory & iterations depending on available resources  |
|                         | Same Initialization Vector      | Reusing Initialization Vectors per encryption under the same key           | Use random IV per message (`random_per_message`)           |
| `crypto_config_we.yaml` | No JWT signature                | Without signature anyone can forge tokens                                  | Use asymetric signing algoritm RS256 from jwt library      |
|                         | No signature verification       | Same as above — accepts forged tokens                                      | Always verify signatures and validate token structure      |
|                         | To small key size               | 1024-bit key is too small for the modern applications                      | Use 3072+ keys                                             |
|                         | Claims validation disabled      | Tokens never expire + audience enables token replay across services        | Require and validate expiration aud audience               |
|                         | Week password hashing algo      | SHA-1 is weak for collision resistance, has no salt                        | Use bcrypt, scrypt or Argon2 with appropriate cost         |
|                         | Encryption w/out authentication | AES-CBC does not provide authentication -> there is no intergity check     | Use AES-GCM                                                |
|                         | Too small key length            | 128-bit key is too small for the modern applications                       | Use 256-bit key                                            |
|                         | Same Initialization Vector      | Reusing Initialization Vectors per encryption under the same key           | Use random IV per message (`random_per_message`)           |

### Homework: Cryptographic protection design for a medical records storage microservice

#### Data requiring protection

- **Patient identity**: full name, date of birth, address, phone/email, national IDs, insurance number, fiscal code, emergency contacts.
- **Clinical data**: diagnoses, conditions, allergies, medications, lab results, reports, clinician notes, treatment plans, procedures, vaccination history.
- **Medical media**: X-ray nd MRI images, ultrasound videos, pathology slides, attached PDFs, scans od documents.
- **Operational and metadata**: appointment history, care team assignments, facility/location metadata, device identifiers from clinical systems.
- **Authentication/authorization data**: user accounts (clinicians, staff, patients), roles, scopes, session tokens, refresh tokens, API keys, service identities.
- **Logs**: who accessed which record, when, from where, what action was performed.

#### Potential threats

1. **Spoofing (S)** – impersonating a user or service

Example: attacker steals a service token and calls the “records” API as an internal microservice; or forges a JWT if algorithm acceptance is misconfigured.

2. **Tampering (T)** – unauthorized modification of data

Example: modifying a patient’s medication list in transit between services, or altering stored records/images to hide malpractice or fraud.

3. **Repudiation (R)** – inability to prove who performed an action

Example: a clinician denies having accessed or edited a record; audit logs are incomplete, not integrity-protected, or are modifiable by application admins.

4. **Information Disclosure (I)** – leaking confidential data

Example: database snapshot exfiltration, misconfigured object storage bucket, logs containing raw PHI, weak encryption/keys, or broken tenant isolation.

5. **Denial of Service (D)** - disruption of system availability

Example: overloading the service APIs with excessive traffic or exploiting vulnerabilities to consume resources, making the system unusable by legitimate users.

6. **Elevation of Privilege (E)** - unauthorized access to higher-level permissions

Example: accessing confidential resources or performing administrative functions through corrupted RBAC/ABAC.

#### Cryptographic protection mechanisms

- **Secrets hashing**: hashed passwords with Argon2id algorithm and per-password random salt handled by the library.

Reason: Slows offline cracking and protects even if the credential DB is leaked.

- **Data encryption**: data that requires protection is encrypted using the AES-256-GCM algorithm to ensure confidentiality and integrity.

Reason: Protects even if the attackers gained physical access to the DB, limits blast radius (per-object keys).

- **Data transmission protection**: external traffic via TLS 1.3 with strong cipher suites, traffic between microservices via mTLS (mutual TLS).

Reason: Prevents eavesdropping and most spoofing/tampering on internal networks.

- **Message signing (beyond TLS)**: sign payloads using HMAC-SHA-256 with per-service keys.

Reason: TLS and mTLS protect “in transit”, while signatures protect “in motion and at rest” (queue, replay, tampering, forensic proof).

- **Key storage method**: JWT signing keys stored in KMS with regular rotation.

Reason: removing the keys handling from app nodes sharply increases security and reduces compromise impact.

- **Audit and access control**: Strong RBAC/ABAC with immutable, integrity-protected audit logs.

Reason: “minimum necessary” access, tenant isolation, break-glass workflow with additional auditing improves security and redices blast impact.

```yaml
  external_tls:
    min_version: "1.3"               # TLS 1.3 only
    hsts_enabled: true               # Enforce HTTPS for clients (where applicable)
  service_mesh_mtls:
    enabled: true                    # Mutual TLS between microservices
    mode: strict                     # Reject non-mTLS internal calls

encryption:
  algorithm: AES-GCM                 # Modern encryption algorithm
  key_length: 256                    # Appropriate key length
  iv_strategy: random_per_message    # Individual Initialization Vector per message
  key_management:
    strategy: envelope_encryption    # keys are generated per object/record and wrapped by KMS
    kms_provider: aws_kms            # Secret manager
  rotation:
    enabled: true                    # Rotation of keys enabled

  hash_function: argon2id            # Best practice for password hashing
  time_cost: 3                       # Multiple passes increase work factor
  memory_cost: 65536                 # 64 MiB makes large-scale cracking expensive
  parallelism: 2                     # Parallelism without avoid excessive contention
  salt_length: 16                    # Random per-password salt generated by the library

message_security:
  signing:
    enabled: true
    algorithm: Ed25519               # Fast, modern signatures; small keys
    key_storage:
      type: kms                      # Keep private signing key in KMS/HSM if available
      key_id: ${KMS_SIGNING_KEY_ID}

  authorization:
    model: rbac_abac                 # Roles + attributes (tenant, department, patient assignment)

  enabled: true
  log_integrity:

    algorithm: SHA-256               # Modern, widely supported
```

#### Summary:

**Critical cryptographic measures**

- TLS 1.3 + mTLS for service-to-service as it prevents spoofing/tampering/disclosure inside the cluster.
- Encryption at rest with AES-256-GCM.
- Strong JWT validation (signature verification, allow-list algorithms, required claims, short TTL).
- Password hashing with Argon2id and rehash policy (protects credential database).
- Tamper-evident, immutable audit logs (required for repudiation control and compliance posture).

**Desirable but not strictly required**

- Message signing for all inter-service calls if strict mTLS is enforced.
- Per-field/column encryption in addition to per-record encryption for especially sensitive data.
- Client-side encryption for certain uploads such as patient-submitted private documents.

**Mistakes to avoid**

- Hardcoding secrets/keys in YAML, code, images, or CI logs.
- Fixed IV/nonce for any encryption mode (especially GCM).
- Accepting JWT alg=none, skipping claim validation, or allowing long-lived tokens.
- Using encryption modes without integrity protection such as AES-CBC.
- Weak password hashing (SHA-1, low-cost Argon2 parameters).
- Missing or mutable audit logs (no integrity protection, no immutability).
